# تقرير اعتماد MVP وإغلاق P0 ومراجعة جاهزية Alpha

**التاريخ:** 2026-07-27  
**المرجع النطاقي:** [Khedmah Digital MVP Definition](../product/KHEDMAH-DIGITAL-MVP-DEFINITION.md)  
**خط المقارنة السابق:** [تقرير برنامج الإصلاحات الجوهرية](comprehensive-remediation-program-2026-07-27.md)  
**قرار الإصدار:** **No-Go للانتقال إلى Alpha حالياً**

## 1. الملخص التنفيذي

اعتمدت هذه الدورة تعريف MVP رسمي ومحدود لثماني قدرات فقط، مع معايير قبول قابلة للتحقق وقائمة صريحة للمستبعد والمؤجل. كما صولحت وثائق النطاق النشطة، ووُسمت تقارير الجاهزية التاريخية بأنها مستبدلة. لم تضف الدورة أي ميزة أو API أو شاشة أو جدول.

البناء والاختبارات مستقران: نجح `npm ci`، ونجح بناء مساحتي العمل، ونجح 467/467 اختباراً. لكن المشروع **غير جاهز لـAlpha** لأن بوابات الأمن والاعتماديات وسلطة البيانات/persistence والدليل المركزي وجودة الكود الكاملة لم تغلق. يسجل التدقيق 1 حرجة و6 عالية و2 متوسطة و0 منخفضة. ولا تزال قدرات MVP الثماني دون حالة «مكتملة» عند تطبيق معايير القبول الجديدة كاملة، رغم أن ستاً منها تملك أساساً عاملاً يحتاج تحسيناً.

**المؤشر الحالي:** جاهزية المشروع الهندسية 63% دون تغير عن التقرير السابق، وإنجاز قبول MVP الرسمي 55% كخط أساس جديد. اختلاف المؤشرين مقصود: الأول يقيس العمل الهندسي الأوسع، والثاني لا يحتسب إلا قدرات MVP الثماني.

## 2. الإنجازات منذ التقرير السابق

1. اعتماد تعريف رسمي لـMVP وإزالة الغموض بين «foundation-only» ووجود runtime فعلي.
2. تحديد ثماني قدرات مطلوبة ومعايير قبول لكل قدرة.
3. تثبيت المستبعد والمؤجل، بما يحمي `أنا مع خدمة` وKhedmah Connect وبقية الاتجاهات المستقبلية من التوسع المبكر.
4. تحديث V1 Scope وProject Charter وExecutive Engineering Directive وDefinition of Done وProduct Backlog لتشير إلى سلطة واحدة.
5. وسم تقارير الدمج/الاستعادة القديمة بأنها أدلة تاريخية وليست اعتماد إصدار.
6. إغلاق P0 الخاص بتعريف MVP وP0 الخاص بالادعاءات التاريخية؛ بقيت خمسة P0 مفتوحة.
7. إعادة تقييم كل وحدة داخل MVP فقط وعدم إدخال المؤجل أو المستبعد في نسبة 55%.
8. إعادة التحقق من البناء والاختبارات والتدقيق الأمني وروابط الوثائق.

## 3. تعريف MVP المعتمد

### الوظائف المطلوبة

| الرمز | الوظيفة الأساسية | الحد الملزم |
| --- | --- | --- |
| MVP-01 | صحة المنصة والإعداد الآمن | health versioned، إعدادات آمنة، سياق طلب وأخطاء آمنة. |
| MVP-02 | الحساب والمصادقة والجلسة والملف الأساسي | تسجيل، دخول، خروج، جلسة، قراءة المستخدم وتحديث الحقول المعتمدة. |
| MVP-03 | المؤسسة والعضوية الأساسية | إنشاء/قراءة/تحديث المؤسسة وإدارة العضوية بصلاحيات محدودة. |
| MVP-04 | تواصل مضبوط مع نشاط تجاري | استفسار ونية تواصل لنشاط مؤهل مع خصوصية وحد إساءة/معدل. |
| MVP-05 | استقبال تحليلات تشغيلية دنيا | أربعة أحداث allowlisted فقط دون تتبع أو ذكاء سوق. |
| MVP-06 | تجربة عربية RTL | رحلات الهوية والمؤسسات وحالات التحميل/الخطأ/التحقق والوصول. |
| MVP-07 | persistence وترحيلات عكوسة | سلطة migration واحدة وتخزين دائم لبيانات MVP فقط. |
| MVP-08 | دليل audit داخلي | أدلة آمنة لنتائج الهوية والمؤسسة والتواصل والتحليلات. |

معايير القبول التفصيلية، التي تتضمن الاستمرارية بعد إعادة التشغيل، الاختبارات الطرفية، الخصوصية، rollback، وعدم تسريب الأسرار، موجودة في الوثيقة المعتمدة ولا يجوز اختزالها في وجود ملف أو route.

### المستبعد من MVP

- Marketplace والمنتجات والمخزون والطلبات والدفع والعمولات والإعلانات والترتيب المدفوع.
- التتبع الفردي/GPS/الأجهزة والسلوك، والشبكات الاجتماعية والتغذية والتعليقات والتفاعلات.
- التوصيات والتصنيف الآلي ودرجات الثقة/الائتمان وذكاء السوق المتقدم وبيع البيانات.
- أي API أو شاشة أو جدول أو تكامل جديد لا يخدم MVP-01 إلى MVP-08 مباشرة.

### المؤجل لما بعد MVP

- Khedmah Connect و`أنا مع خدمة` كتعبير مستقبلي للعلامة/المجتمع.
- Job Work وKhedmah Sharing الأوسع وشبكة الشركاء والممثلين.
- التدفقات الكاملة للكتالوج والمواقع والعلاقات والثقة والملفات المهنية/التجارية والاكتشاف والبحث العام.
- التحليلات وذكاء السوق المتقدمان.

## 5. سجل المهام الحرجة P0

### P0-01 — اعتماد تعريف MVP

- **المشكلة:** لم يوجد تعريف واحد يحدد الوظائف ومعايير القبول والمستبعد والمؤجل.
- **سبب الحرج:** لا يمكن حساب الإنجاز أو منع التوسع أو اتخاذ قرار Alpha دون مقام رسمي.
- **الأثر:** نسب وتقارير متعارضة وإمكانية تنفيذ غير مصرح.
- **خطة المعالجة:** وثيقة سلطة واحدة، ثم تحديث النطاق والميثاق وDoD والbacklog.
- **الحالة:** **مغلقة في هذه الدورة.**

### P0-02 — ثغرات Next.js وسلسلة الواجهة

- **المشكلة:** `next@15.4.4` عقدة مباشرة حرجة وتجمع تنبيهات RCE وSSRF وDoS وXSS/cache، مع `sharp` و`postcss` انتقاليتين عاليتين.
- **سبب الحرج:** Next يشغل واجهة MVP مباشرة؛ عدم استخدام بعض الخصائص يخفض التعرض ولا يغلق التنبيه.
- **الأثر:** حاجز أمني صريح أمام Alpha.
- **خطة المعالجة:** ترقية ضيقة داخل 15.x إلى إصدار مصحح مدعوم، مع React/React DOM المتوافقين فقط، ثم build و467 اختباراً وsmoke RTL وaudit قبل/بعد. يمنع الانتقال إلى Next 16 في هذه الدفعة.
- **الحالة:** **مفتوحة — لم تنفذ الترقية لأن المهمة الحالية وثائق/اعتماد ولأن الدفعة تحتاج مراجعة مستقلة.**

### P0-03 — ثغرات NestJS وسلسلة الخلفية

- **المشكلة:** `@nestjs/core` و`@nestjs/platform-express` مباشرتان عاليتان، و`@nestjs/common` مباشرة متوسطة، مع `multer`, `path-to-regexp`, و`file-type` انتقالية.
- **سبب الحرج:** الحزم تشغل كل API في MVP؛ عدم وجود upload يقلل Multer فقط.
- **الأثر:** DoS/injection محتمل وحاجز أمني أمام Alpha.
- **خطة المعالجة:** ترقية حزم Nest الثلاث معاً داخل 11.x إلى patch متوافق، ثم audit لشجرة الانتقاليات واختبارات health/identity/organizations/contact/analytics.
- **الحالة:** **مفتوحة.**

### P0-04 — غياب remote ودليل CI مركزي

- **المشكلة:** لا يوجد remote في `.git/config` المحلي.
- **سبب الحرج:** لا يمكن إثبات أن الفرع يطابق المصدر الرسمي أو أن workflows نجحت على المرشح نفسه.
- **الأثر:** كل أدلة الاستقرار محلية فقط.
- **خطة المعالجة:** يضيف مسؤول المستودع remote موثوقاً، ينفذ fetch/prune ومقارنة SHA، ثم يسجل رابط CI للمرشح.
- **الحالة:** **مفتوحة/محجوبة إدارياً.**

### P0-05 — سلطة migration وrollback

- **المشكلة:** مساران متوازيان للـSQL ولا توجد تجربة PostgreSQL موحدة.
- **سبب الحرج:** خطر ترتيب/lineage وفشل rollback أو اختلاف runtime عن المخطط.
- **الأثر:** يمنع قبول MVP-07 وأي Alpha ببيانات دائمة.
- **خطة المعالجة:** ADR يختار سلطة واحدة، يجمد الأخرى، ثم forward/rollback على قاعدة مؤقتة دون إضافة جداول خارج MVP.
- **الحالة:** **مفتوحة وتحتاج قرار الإدارة/العمارة.**

### P0-06 — ادعاءات الجاهزية التاريخية

- **المشكلة:** تقارير قديمة تعلن Production Ready و100% رغم غياب الأدلة الحالية.
- **سبب الحرج:** يمكن أن تقود إلى قرار إطلاق خاطئ.
- **الأثر:** خطر حوكمة وتدقيق.
- **خطة المعالجة:** وسم الملفات التاريخية كمستبدلة وربط القرار الحالي بتعريف MVP وبوابات Alpha.
- **الحالة:** **مغلقة في هذه الدورة.**

### P0-07 — persistence المطلوب يعمل داخل الذاكرة

- **المشكلة:** بيانات الحساب والجلسة والمؤسسة والتواصل والتحليلات وحدود المعدل تضيع عند restart ولا تتشارك بين النسخ.
- **سبب الحرج:** يخالف معايير MVP-02/03/04/05/07/08 ولا يسمح بسلوك Alpha موثوق.
- **الأثر:** فقد بيانات، تجاوز rate limit في multi-instance، وعدم إمكانية اختبار النزاهة.
- **خطة المعالجة:** بعد P0-05 فقط، توصيل مستودعات MVP الحالية بالسلطة المعتمدة واختبار restart/referential integrity/multi-instance دون إضافة وظيفة.
- **الحالة:** **مفتوحة.**

### حصيلة P0

- **مغلق:** 2 (`P0-01`, `P0-06`).
- **مفتوح:** 5 (`P0-02`, `P0-03`, `P0-04`, `P0-05`, `P0-07`).
- **لا يجوز وصف برنامج P0 بأنه مغلق بالكامل.**

## 6. خطة الأمن المرحلية

| الأولوية | الحزمة/السلسلة | الشدة | أثرها الحالي | دفعة المعالجة | شرط الإغلاق |
| --- | --- | --- | --- | --- | --- |
| S0 | `next` | حرجة | runtime مباشر؛ بعض الخصائص غير مستخدمة لكن RCE/SSRF/DoS/XSS مجمعة | A | إصدار 15.x مصحح، audit بلا critical، smoke/build/tests. |
| S0 | `@nestjs/core`, `@nestjs/platform-express` | عالية | runtime API مباشر | B | Nest 11.x متناسق وغياب high الناتجة عنهما. |
| S1 | `sharp`, `postcss` | عالية انتقالية | لا next/image أو CSS مستخدم غير موثوق حالياً | A | إغلاقها عبر شجرة Next الجديدة. |
| S1 | `multer`, `path-to-regexp` | عالية انتقالية | لا upload/wildcards معقدة حالياً، لكنها ضمن runtime | B | إغلاقها عبر Nest/platform-express والتحقق من routes. |
| S2 | `@nestjs/common`, `file-type` | متوسطة | common مباشر، ولا معالجة ملف مرفوع حالياً | B | إغلاق/قبول موثق بعد audit الجديد. |

### تسلسل الترقية

1. تثبيت خط الأساس الحالي وSHA ونتائج build/test/audit.
2. دفعة A تعدل Next/React/React DOM وlockfile فقط، ولا تغير كود المنتج.
3. إذا نجحت A تدمج مستقلة؛ إذا فشلت يرجع التزامها كاملاً.
4. دفعة B تعدل حزم Nest الثلاث وlockfile فقط، ثم smoke لكل controller.
5. دفعة C لاحقة لأدوات التطوير patch/minor؛ يمنع TypeScript 7 وNode types 26 والترقيات الرئيسية في برنامج الأمن الحالي.
6. لا يستخدم `npm audit fix --force` دون قرار مجلس لاحق يحدد الأثر وخطة الرجوع.

## 11. قرارات تحتاج اعتماد الإدارة

1. **اختيار سلطة migration:** `backend/migrations` أو `infra/database`، مع تجميد الأخرى.
2. **تسمية runtime authority:** تحديد علاقة `apps/backend` مع foundations في `backend/` عبر ADR.
3. **اعتماد عتبة Alpha الأمنية:** التوصية صفر critical وصفر high في production dependencies، وأي استثناء باسم ومالك وتاريخ انتهاء.
4. **تعيين remote الرسمي وصلاحية CI:** مسؤول محدد ومصدر موثوق.
5. **اعتماد خطة دفعتَي A وB:** ترقيات ضيقة منفصلة دون تحديث رئيسي أو `npm audit fix --force`.
6. **سياسة persistence لـAlpha:** التوصية عدم قبول Maps للبيانات المطلوبة؛ إن قبل استثناء فيجب أن يكون محدوداً وغير إنتاجي وموثقاً.

## 13. التوصية النهائية

### القرار: No-Go إلى Alpha

البناء والاختبارات وحدهما غير كافيين. الأدلة المانعة هي: 1 critical و6 high في الاعتماديات، خمس مهام P0 مفتوحة، غياب persistence دائم وسلطة migration واحدة، غياب CI مركزي قابل للتحقق، وعدم اكتمال أي من قدرات MVP الثماني وفق معايير القبول الكاملة.

يعاد تقييم Go/No-Go فقط بعد إغلاق P0-02 حتى P0-05 وP0-07، نجاح بوابات الأمن والاعتماديات والجودة والتوثيق المركزية، ثم تحديث لوحة MVP دون احتساب أي وحدة مؤجلة أو مستبعدة.
