# Mission-024 — Critical P0 Security Foundation Hardening

**التاريخ:** 2026-07-27  
**المهمة المختارة:** P0-02 — ثغرات Next.js وسلسلة الواجهة  
**الحالة:** خُفّض الخطر بوضوح؛ أزيلت الحالة الحرجة، وبقيت P0-02 مفتوحة لمعالجة انتقاليات عالية  
**قرار Alpha:** No-Go — ما زالت بوابات أمن وP0 أخرى مفتوحة

## 1. الملخص التنفيذي

راجعت Mission-024 مهام P0 الخمس المفتوحة واختارت P0-02 لأنها كانت الوحيدة المرتبطة بعقدة تبعية **حرجة مباشرة** (`next@15.4.4`) في runtime واجهة MVP. نفذت المهمة ترقية ضيقة داخل الجيل نفسه إلى `next@15.5.22` ولم تغير React أو كود المنتج أو نطاق MVP.

أزالت الترقية كل تنبيهات Next المباشرة التي كان npm يجمعها قبل التعديل، فانخفض عدد العقد الحرجة من 1 إلى 0. بقيت عقدة `next` مصنفة high فقط لأنها ترث تنبيهي `postcss` و`sharp` الانتقاليين؛ لذلك لم تغلق P0-02 إدارياً. ارتفع عداد العقد العالية من 6 إلى 7 نتيجة إعادة تصنيف عقدة Next نفسها من critical إلى high، وليس بسبب إضافة تنبيه مباشر جديد. بقي إجمالي عقد الحزم المتأثرة 9.

نجح التثبيت النظيف والبناء وجميع الاختبارات 467/467 بعد الترقية. لم تستخدم المهمة `npm audit fix --force`، ولم تضف override إلى `sharp` أو `postcss`، لأن فرض إصدار خارج قيود Next دون اختبار توافق مستقل سيكون تغييراً واسعاً غير مبرر في هذه المهمة.

### سبب اختيار P0-02

1. `next` تبعية إنتاج مباشرة تشغل كل صفحات الواجهة داخل MVP.
2. خط الأساس من `npm audit --json` صنف عقدتها critical، بينما لم تحمل أي P0 أخرى عقدة تبعية critical.
3. المعالجة متاحة كترقية backport محدودة من 15.4.4 إلى 15.5.22 داخل major 15، فلا تحتاج توسيع نطاق أو إعادة تصميم.
4. P0-07 قد يساويها أو يفوقها في أثر سلامة البيانات عند تشغيل Alpha متعدد النسخ، لكنه محجوب بقرار P0-05 ويتطلب تغيير persistence واسعاً. لذلك كان اختيار P0-02 أعلى خفض خطر يمكن إنجازه مستقلاً في Mission واحدة.

## 3. التحليل الفني قبل التعديل

### الملفات التي روجعت

- `apps/frontend/package.json`: نسخة Next المباشرة وسكربتات البناء والاختبار.
- `package-lock.json`: نسخ `next`, `react`, `react-dom`, `postcss`, و`sharp` الفعلية.
- `apps/frontend/next.config.ts`: لا توجد `remotePatterns`, rewrites, redirects, أو إعدادات صور خارجية.
- جميع ملفات `apps/frontend` عدا `.next`: لا استخدام لـ`next/image`, Server Actions, middleware, أو custom image handlers.
- تقرير P0 السابق و`docs/product/PRODUCT-BACKLOG.md`: تعريف الخطر وخطة الدفعة A وحدودها.
- مخرجات `npm audit --json` قبل التعديل: 1 critical، 6 high، 2 moderate، 0 low، وإجمالي 9 عقد متأثرة.

### سبب المشكلة

كان manifest يسمح بـ`next@^15.4.4` وكان lockfile يثبت 15.4.4. هذه النسخة تقع ضمن نطاق عدد كبير من تنبيهات Next المباشرة التي يعرضها npm، إضافة إلى انتقاليات `postcss@8.4.31` و`sharp@0.34.5`.

### الأثر الأمني

- كانت عقدة Next المباشرة تجمع مخاطر RCE وSSRF وDoS وXSS وcache confusion/poisoning بحسب بيانات npm audit المحلية.
- عدم وجود Server Actions أو middleware أو صور خارجية يخفض تعرض بعض المسارات، لكنه لا يغلق عقدة runtime حرجة ولا يبرر Alpha.
- `postcss` و`sharp` تبقيان خطراً انتقالياً حتى مع عدم استخدام CSS غير موثوق أو `next/image` حالياً؛ قد يتغير التعرض إذا تغير الاستخدام مستقبلاً.

### أثر الاستقرار

- أي ترقية major إلى Next 16 ستوسع أثر التغيير، وقد تغير متطلبات Node والبناء وسلوك App Router.
- فرض `sharp@0.35` أو `postcss@8.5.18` عبر overrides دون أن تعلن سلسلة Next 15 توافقها يحتاج مهمة مستقلة واختبارات صور/CSS؛ لذلك لم ينفذ.
- الترقية المختارة بقيت داخل Next 15 ولم تغير React 19.1.0 أو React DOM 19.1.0.

## 4. التنفيذ

### التعديلات المنفذة

1. تحديث `apps/frontend/package.json` من `next@^15.4.4` إلى `next@^15.5.22`.
2. مزامنة `package-lock.json` بواسطة npm لتثبيت Next 15.5.22 وشجرته المتوافقة.
3. عدم تعديل React، React DOM، TypeScript، كود الواجهة، routes، الشاشات، أو أي قدرة MVP.
4. عدم استخدام `npm audit fix` أو `npm audit fix --force`.
5. عدم إضافة overrides أو ترقيات Nest؛ P0-03 مهمة مستقلة تالية.

### تفسير صريح لارتفاع high

قبل الترقية كانت عقدة `next` تحسب critical لأنها احتوت تنبيهات Next مباشرة إضافة إلى انتقالياتها. بعد الترقية لم يعد حقل `via` يحتوي أي advisory object مباشر لـNext؛ بقي فقط الاسمان `postcss` و`sharp`. npm يصنف عقدة Next high بالوراثة منهما، فتنتقل عقدة واحدة من عمود critical إلى high. لذلك المقياس الأكثر دلالة لهذه المهمة هو إزالة critical والتنبيهات المباشرة، مع عدم الادعاء أن سلسلة الواجهة أصبحت خالية من high.

## 8. المخاطر المتبقية

1. `postcss` و`sharp` انتقاليتان high وترفعان عقدة Next إلى high.
2. P0-03 Nest ما زالت تحتوي عقداً مباشرة وانتقالية high وmoderate.
3. لا remote أو دليل CI مركزي؛ الأدلة الحالية محلية.
4. سلطة migrations وpersistence ما زالت P0 مفتوحة وتمنع Alpha.
5. لا browser E2E أو اختبار next/image؛ لذا لا يجوز فرض override لسلسلة الصور دون توسيع التحقق أولاً.
6. بوابة الأمن ما زالت فاشلة لأن معيار Alpha المعتمد يتطلب صفر critical وصفر high ما لم يمنح المجلس استثناء زمنياً.

## 9. توصية P0 التالية

**التوصية: تنفيذ P0-03 — ترقية حزم Nest الثلاث ضمن 11.x كـMission مستقلة.**

السبب:

- هي أعلى P0 أمنية متبقية ويمكن تنفيذها بترقية patch/minor مترابطة تقنياً لـ`@nestjs/common`, `@nestjs/core`, و`@nestjs/platform-express`.
- يتوقع أن تعالج عقد `multer`, `path-to-regexp`, و`file-type` أو تخفضها، مع إمكانية التحقق عبر health وidentity وorganizations وcontact وanalytics.
- لا ينبغي دمجها مع معالجة `sharp`/`postcss` في Mission-024 لأنها سلسلة backend مستقلة، ولأن المجلس منع تنفيذ أكثر من P0 غير مترابطة في المهمة نفسها.

بعد P0-03، يجب إجراء قرار تقني منفصل بشأن انتقاليات Next المتبقية: انتظار backport متوافق أو اختبار overrides محددة؛ يمنع الانتقال التلقائي إلى Next 16 أو استخدام `--force`.

## 10. قرار Alpha

**No-Go.** إزالة critical إنجاز جوهري، لكنها لا تغلق بوابة الأمن: ما زال audit يسجل 7 high و2 moderate، وما زالت خمس مهام P0 مفتوحة. يعاد تقييم Alpha بعد P0-03 ومعالجة/اعتماد انتقاليات Next، ثم إغلاق سلطة البيانات والدليل المركزي وبقية البوابات المعتمدة.
