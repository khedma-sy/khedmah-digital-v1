# تقرير تحليل الصور المعتمدة 1–5 ورحلة المستخدم

## 1. القرار التنفيذي

هذا تقرير **تحليل وفحص فقط قبل أي تنفيذ إضافي** وفق [حوكمة الصور المرجعية](../product/IMAGE-DRIVEN-UX-GOVERNANCE.md). فحص التقرير التطبيق الموجود في المستودع، ولم يفترض أن التشابه البصري يعني اكتمال القدرة.

النتيجة وقت التدقيق: **REPAIR BEFORE IMPLEMENTATION**. الصور الخمس صنعت تسلسلاً بصرياً جيداً، لكن الحقن وقتها احتوى أفعالاً جزئية أو مضللة. عولجت نتائج هذا التدقيق لاحقاً، وحالة ما بعد الإصلاح محفوظة في [الملف المرجعي لمعالجة الصور 1–5](images-1-5-remediation-reference-2026-08-09.md). تبقى الأقسام التالية سجلاً تاريخياً لحالة ما قبل المعالجة وليست وصفاً للحالة الحالية.

## 2. الرحلة المقصودة للصور الخمس

| الترتيب | الصورة | الدور | نقطة الدخول | الخروج الصحيح |
| --- | --- | --- | --- | --- |
| 1 | تسجيل الدخول | مستخدم قائم | «ابدأ الآن» ثم تسجيل الدخول | الرئيسية أو الوجهة الأصلية |
| 2 | إنشاء حساب | مستخدم جديد | «إنشاء حساب» | نجاح التسجيل ثم تهيئة أول مرة |
| 3 | خريطة/أنا مع خدمة | ترحيب أول مرة | نجاح إنشاء الحساب | الرئيسية؛ مع إمكانية التخطي |
| 4 | الرئيسية | اكتشاف خدمة مركزية | دخول/ترحيب/زيارة عامة | فئة الخدمة أو البحث |
| 5 | خدمات منزلية | قائمة فئة | الضغط على «خدمات منزلية» | نتائج حقيقية ثم ملف مقدم الخدمة |

المسار النهائي المعتمد لهذه الحزمة: `register/login → welcome (مرة واحدة) → / → service category → search result → provider profile → contact`.

## 3. الصورة الأولى — تسجيل الدخول

### 3.1 التحليل

هيكلها مناسب: هوية، معرف دخول، كلمة مرور، إجراء أساسي، فاصل، إنشاء حساب، ومساعدة. يجب ألا تتحول المساحة البصرية العلوية إلى عائق أمام لوحة المفاتيح أو قارئ الشاشة.

### 3.2 القابلية للتطبيق

| العنصر | القرار | السبب |
| --- | --- | --- |
| البريد/الهاتف | تعديل | backend الحالي يسجل بالبريد؛ عبارة الهاتف توحي بقدرة غير مثبتة |
| كلمة المرور والعين | تطبيق | مدعومة؛ زر العين أصبح فعلياً |
| نسيت كلمة المرور | حذف مؤقت/تأجيل | الرابط الحالي يفتح التسجيل وليس استعادة كلمة المرور |
| تسجيل الدخول | تطبيق | متصل بـ`api.auth.login` |
| إنشاء حساب | تطبيق | مسار موجود |
| «الاستمرار زائراً» | تعديل | يجب أن يفتح الرئيسية العامة، لا رابط بريد إلكتروني |

### 3.3 فحص الحقن الحالي

| العنصر | الحالة | الدليل/المشكلة |
| --- | --- | --- |
| تسجيل الدخول | يعمل | يرسل البريد وكلمة المرور ثم يفتح `/organizations` |
| إظهار كلمة المرور | يعمل | state وزر وصول موجودان |
| إنشاء حساب | يعمل | يفتح `/auth/register` |
| نسيت كلمة المرور | **لا يعمل بوظيفته** | يفتح `/auth/register` |
| الاستمرار زائراً | **لا يعمل بوظيفته** | النص غير واضح والرابط `mailto` |
| «البريد أو الهاتف» | **جزئي** | input من نوع email والـAPI يستقبل email فقط |

### 3.4 المنجز وغير المطبق

- منجز: الشكل العربي، الاتصال بالمصادقة، loading/error، التسجيل، زر العين.
- غير مطبق: استعادة كلمة المرور، دخول الهاتف، مسار زائر واضح، اختبار browser E2E للجلسة الفعلية.

### 3.5 تقييم التصميم

**7.4/10**: بصرياً قوي، لكن يلزم حذف الزخرفة الزائدة على الشاشات القصيرة، وتصحيح ثلاثة وعود وظيفية قبل الاعتماد.

## 4. الصورة الثانية — إنشاء حساب

### 4.1 التحليل

ترتيب البيانات واضح، لكن مؤشرات 1–2–3 تعني رحلة متعددة المراحل. لا يجوز عرضها إذا كان التطبيق نموذجاً واحداً ينتهي مباشرة.

### 4.2 القابلية للتطبيق

| العنصر | القرار | السبب |
| --- | --- | --- |
| الاسم والبريد وكلمة المرور | تطبيق | مدعومة في عقد التسجيل الحالي |
| الهاتف | تأجيل أو ربط بعقد | موجود بصرياً لكنه لا يرسل إلى API |
| تأكيد كلمة المرور | تطبيق | تحقق محلي صحيح |
| قوة كلمة المرور | تعديل | النص الحالي ثابت ولا يقيس حرفاً كبيراً أو رقماً |
| المراحل 1–2–3 | حذف حالياً | لا توجد صفحات تحقق وتهيئة فعلية بهذا التسلسل |
| الشروط والخصوصية | حجب حتى وجود الصفحات | المساران غير موجودين في build الحالي |

### 4.3 فحص الحقن الحالي

| العنصر | الحالة | المشكلة |
| --- | --- | --- |
| إنشاء الحساب | يعمل للبريد/الاسم/كلمة المرور | يستدعي `api.auth.register` |
| الهاتف | **غير محقون** | لا يدخل payload |
| تأكيد كلمة المرور | يعمل | يمنع عدم التطابق |
| معيار حرف كبير/رقم | **غير مطبق** | إرشاد ثابت فقط؛ `minLength=8` هو القيد الحقيقي |
| الشروط/الخصوصية | **لا تعمل** | `/terms` و`/privacy` غير مولدين |
| المراحل | **شكلية** | لا توجد state machine أو تنقل بينها |

### 4.4 المنجز وغير المطبق

- منجز: التسجيل الأساسي، تطابق كلمة المرور، loading/error، الانتقال إلى `/welcome`، أزرار العين.
- غير مطبق: رقم الهاتف، التحقق، التهيئة كمرحلتين، سياسة كلمة مرور كاملة، صفحات السياسات.

### 4.5 تقييم التصميم

**6.8/10**: الترتيب جميل، لكن كثافة النموذج كبيرة ووجود مراحل وسياسات وهاتف غير محقونة يخفض الثقة. الأفضل نموذج صادق أقصر.

## 5. الصورة الثالثة — خريطة سوريا والترحيب

### 5.1 التحليل

هي شاشة هوية/تهيئة وليست صفحة عمل يومية. فائدتها تعريف الشبكة والانتقال، ويجب ألا تُجبر المستخدم على رؤيتها بعد كل دخول.

### 5.2 القابلية للتطبيق

| العنصر | القرار | السبب |
| --- | --- | --- |
| الخريطة والمحافظات | تطبيق بصري مضبوط | لا تعني تفعيل خدمات مكانية أو تتبع موقع |
| «أنا مع خدمة» | إبقاء كتعبير هوية مستقبلي | لا تعرض كعضوية أو ضمان فعلي |
| متابعة للرئيسية | تطبيق | خروج واضح |
| مشاركة | تعديل/تأجيل | تبقى فقط إذا كانت مشاركة آمنة ومفهومة |
| التكرار | حذف | تظهر أول مرة فقط أو يمكن تجاوزها |

### 5.3 فحص الحقن الحالي

| العنصر | الحالة | المشكلة |
| --- | --- | --- |
| حماية الجلسة | تعمل | غير المصادق يعاد إلى login |
| اسم المستخدم | يعمل | من session profile |
| المتابعة | تعمل | تفتح `/` |
| المشاركة | جزئية | المكوّن موجود؛ يحتاج browser/device validation |
| مرة واحدة فقط | **غير مثبتة** | لا توجد حالة onboarding مكتملة محفوظة في هذا التنفيذ |
| دقة الخريطة | مرجعية فقط | SVG تقريبي وليس مصدراً جغرافياً |

### 5.4 المنجز وغير المطبق

- منجز: جلسة، تخصيص الاسم، خريطة، متابعة، RTL.
- غير مطبق: تذكر اكتمال onboarding، تخطي مستقل، إثبات مشاركة على الأجهزة، دقة جغرافية معتمدة.

### 5.5 تقييم التصميم

**8.0/10** كترحيب أول مرة؛ **4/10** إذا تكرر. يقترح تقليل النص والتوهج وإبقاء CTA واحد.

## 6. الصورة الرابعة — الصفحة الرئيسية

### 6.1 التحليل

الهيكل الصحيح: هوية صغيرة، بحث، فئات أساسية، إثبات ثقة غير مضلل، وتنقل سفلي. يجب أن تكون الرئيسية نقطة قرار لا معرضاً زخرفياً.

### 6.2 القابلية للتطبيق

| العنصر | القرار | السبب |
| --- | --- | --- |
| البحث | تطبيق | مسار `/search` موجود |
| فئات الخدمات | تطبيق إذا كانت taxonomy قانونية | لا تنشئ فئة حية بلا نتائج/API |
| «خدمات موثوقة/تجربة مضمونة» | تعديل | الضمان ادعاء يحتاج عقداً؛ البديل «اكتشف مقدمي الخدمات» |
| التنبيهات | تأجيل/تغيير إلى الحساب | لا توجد قدرة إشعارات معتمدة |
| طلباتي | حذف أو إعادة تسمية | لا توجد قدرة طلبات V1 معتمدة |
| مؤشرات carousel | حذف | لا carousel فعلياً |

### 6.3 فحص الحقن الحالي

| العنصر | الحالة | المشكلة |
| --- | --- | --- |
| البحث | يعمل | يرسل إلى `/search` |
| شعار المنصة | يعمل | يفتح الملف الرسمي |
| أيقونة القائمة | تعمل | تفتح الكتالوج |
| أيقونة الجرس | **مضللة جزئياً** | تفتح `/users/me` لا إشعارات |
| الفئات | **جزئية** | تمرر `?category=` لكن صفحة الكتالوج لا تقرأ query عند التحميل |
| حسابي في الشريط السفلي | **وجهة خاطئة** | يفتح بحث الأعمال لا `/users/me` |
| الرئيسية في الشريط السفلي | **وجهة خاطئة** | تفتح إنشاء ملف أعمال لا `/` |
| طلباتي | **غير موجودة كقدرة** | الرابط يفتح كتالوج الخدمات |
| نقاط الشرائح | **زخرفة بلا فعل** | لا carousel |

### 6.4 المنجز وغير المطبق

- منجز: البحث، العرض RTL، روابط فئات، الملف الرسمي، نظام SVG لمعظم الأفعال.
- غير مطبق: إشعارات، طلبات، carousel، حقن category في الحالة الأولى، تنقل سفلي صادق.

### 6.5 تقييم التصميم

**7.1/10** بصرياً، **5.5/10** وظيفياً. يحذف carousel، وتستبدل وعود الضمان، وتصحح مسميات/وجهات الشريط السفلي.

## 7. الصورة الخامسة — الخدمات المنزلية

### 7.1 التحليل

الصورة تقترح صفحة فئة: رأس ورجوع وفلتر، خدمة مميزة، قائمة خدمات، وتنقل سفلي. الهيكل صالح، لكن البيانات يجب أن تأتي من الكتالوج الحقيقي لا من نص ثابت.

### 7.2 القابلية للتطبيق

| العنصر | القرار | السبب |
| --- | --- | --- |
| الرجوع | تطبيق | مسار واضح |
| الفلتر | تطبيق | يتصل بـAPI ويعرض أثره |
| خدمة مميزة | حذف حتى اعتماد ranking | «الأكثر طلباً» ترتيب غير معتمد |
| الأسعار | بيانات حقيقية فقط | يمنع السعر الثابت التوضيحي في runtime |
| «اطلب الآن» | تغيير إلى «عرض مقدمي الخدمة» | لا توجد قدرة طلب/حجز معتمدة |
| قائمة الخدمات | تطبيق | من API وبحالات loading/error/empty |

### 7.3 فحص الحقن الحالي

| العنصر | الحالة | المشكلة |
| --- | --- | --- |
| الرجوع | يعمل | يفتح `/` |
| الفلتر | يعمل تقنياً | يستدعي البحث بالتصنيف |
| أثر الفلتر | **جزئي/ملتبس** | النتائج الحقيقية قد تظهر أسفل البطاقات الثابتة، لكن عداد النتائج والحالة الفارغة والمرشحات الأصلية مخفية، فلا تعكس الواجهة دائماً أثر الاختيار بوضوح |
| تنظيف/كهرباء/دهان/سباكة | روابط تعمل للبحث | المحتوى والأسعار ثابتة وليست نتائج API |
| «الأكثر طلباً» | **غير محقون ببيانات** | لا ranking أو analytics source |
| «اطلب الآن» | **غير محقون كطلب** | يفتح search فقط |
| الأسعار | **مضللة** | قيم ثابتة لا مصدر لها |
| الشريط السفلي | يعيد أخطاء الصورة الرابعة | المسميات لا تطابق الوجهات/القدرات |

### 7.4 المنجز وغير المطبق

- منجز: shell، الرجوع، فتح الفلتر، استدعاء API، روابط البحث، RTL.
- غير مطبق: دمج نتائج API كالمصدر الوحيد للبطاقات والحالة الفارغة، ranking، أسعار حية، طلب، صورة خدمة من media معتمد، وتنقل سفلي قانوني.

### 7.5 تقييم التصميم

**7.8/10** كهيكل، **4.8/10** كحقن حالي. أفضل تعديل هو إزالة العرض الثابت بالكامل وبناء البطاقة نفسها من `PublicServiceListing`.

## 9. ما يحذف أو يعدل لجمالية واتساق التطبيق

1. حذف مؤشرات الشرائح غير الفعالة.
2. حذف مراحل التسجيل الشكلية أو تنفيذها لاحقاً بعقد مستقل.
3. إزالة الأسعار ووسم «الأكثر طلباً» و«مضمونة» ما لم تكن مستندة إلى بيانات معتمدة.
4. تقليل التوهج والخطوط الصغيرة؛ الحد الأدنى للنص العربي 12px ومنطقة اللمس 44px.
5. توحيد التنقل السفلي في مكوّن واحد، وبنفس المسميات والوجهات في الصفحتين 4 و5.
6. استخدام SVG فقط؛ المظلة النصية `☂` وأسهم Unicode تستبدل بأصول الهوية/الأيقونات الموحدة.
7. جعل الخدمة المركزية والفئة والنتيجة هي التسلسل البصري؛ لا تعرض بطاقة ثقة أكبر من فعل البحث.

## 10. خطة الإصلاح قبل أي تطبيق بصري جديد

1. تصحيح صدق شاشة الدخول والتسجيل: حذف/ربط الأفعال غير الموجودة.
2. حسم onboarding مرة واحدة وتخطيه.
3. إنشاء مكوّن تنقل سفلي قانوني بلا «طلبات» أو «إشعارات» غير معتمدة.
4. قراءة تصنيف الرابط في الكتالوج وإظهار نتائج API فعلياً.
5. حذف البيانات الثابتة والأسعار والترتيب واستبدالها بإسقاط API.
6. ربط كل نتيجة بملف مقدم الخدمة ثم قناة التواصل الحالية.
7. تنفيذ اختبارات browser لكل زر وحالات الشبكة والصلاحية.
8. التقاط صور بعد الحقن عند 360/768/1440 وإصدار تقرير before/after ودرجة نهائية.

حتى إغلاق البنود 1–6، لا توصف الصور الخمس بأنها «مطبقة بالكامل»، ولا يبدأ تصميم الصورة السادسة في الرحلة نفسها.
